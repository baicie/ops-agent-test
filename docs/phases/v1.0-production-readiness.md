# v1.0 详细设计：Production Readiness

- 状态：实现中
- 前置条件：`v0.1-v0.6` 全部阶段门禁通过

本阶段正在落地运维命令、`/readyz`、loopback fail-closed、合同 fixture、运维文档，
以及不打 tag 的 release dry-run（校验和与 SBOM）。
24h soak、签名发布和 `v1.0.0` tag **尚未**作为发布门禁跑过，因此本阶段不能标为已发布。

## 阶段目标

不再增加新的产品能力，集中冻结合同、消除高风险技术债、验证 SLO、安全和升级路径，发布一个
可由单个运维工程师长期运行的本地生产版。

“Production Ready”限定为单进程、单操作者、用户控制环境；不表示 SaaS、多租户、高可用或
无人值守自动修复。

## 最终用户结果

用户可以安装 OpsCodex、创建 Workspace、接入受支持的观测与 Kubernetes 环境，通过 CLI/Web
完成证据化调查，安全恢复长 Thread，并对少量结构化 remediation 做人工批准。升级、备份、
恢复和回滚都有明确、经过演练的路径。

## 范围

### 包含

- `/api/v1`、Event schema、config、Tool descriptor 和 storage schema 稳定承诺。
- 安装包、校验和、SBOM、许可证和可重现 release build。
- 配置检查、readiness、backup/restore、migration/rollback 和诊断命令。
- 完整场景评测、安全威胁测试、性能/容量/长稳测试。
- Runtime metrics、SLO、告警建议和隐私/retention 文档。
- Web/CLI 可访问性、错误恢复和完整操作文档。

### 不包含

- 新 Provider、Connector、Tool、Skill 或 remediation 类型。
- 多实例、远程多用户、SaaS、RBAC、云控制面。
- Multi-Agent、自动 remediation 或通用 Workflow。

## 稳定合同

### API 和 Event

- `/api/v1` 字段采用 additive evolution；移除或改变语义需要新 API major。
- Event schema 保持向前可忽略未知字段、向后兼容最近一个 minor storage version。
- Idempotency-Key、pagination、SSE reconnect、error envelope 和 rate/budget error 被契约测试冻结。
- OpenAPI 或等价机器可读 schema 从 Rust source 生成，并与 Web client 类型做 drift check。

### Storage

- SQLite schema migration 单向前进；每个 release 提供 preflight、backup 和 rollback compatibility。
- 支持在线读取旧 schema、离线迁移和导出 JSONL；不承诺新版本数据被旧 binary 写入。
- Artifact retention、orphan cleanup、disk quota 和 corruption detection 有默认值与 dry-run maintenance。

### Extension

- CapabilityDescriptor、MCP subset、Custom Tool manifest 和 Skill metadata 发布 `v1` schema。
- 未知 major、未 pin version/hash 或不满足 effect metadata 的扩展 fail closed。

## 场景评测

最终 deterministic suite 至少包含：

1. 数据库连接池耗尽：Metrics + Logs + Health。
2. 服务错误激增：Alert + Metrics + Logs。
3. 延迟回归：Metrics + Trace + Topology。
4. Kubernetes workload 失败：K8s status/events/logs + Runbook。
5. 下游依赖故障：Trace + Topology + dependency health。
6. Evidence 不足：正确 abstain，不产生无来源 Claim。
7. Prompt Injection：拒绝越权 Tool/target/change。
8. 安全 remediation：批准成功、拒绝、过期、重放、崩溃对账。

评分器验证结构化事实和不变量，不使用整段答案精确匹配。真实 Provider gate 只验证少量代表性
路径，不能替代 deterministic suite。

## SLO 和容量目标

在发布参考机器、4 个并发 Turn 和记录的 fixture 数据集上：

- 排除外部 Provider/Connector 后，本地 command/projection p95 小于 100 ms。
- Event append 成功率 99.9% 以上；任何失败都在 API/Turn 状态可见。
- SSE 重连投影重复 Item 数为 0，成功确认 Event 丢失数为 0。
- 24 小时长稳测试无 active lease、EventHub、子进程或 artifact handle 泄漏。
- Context、Tool、Artifact 和磁盘 quota 都能提前拒绝并给出可操作错误。
- 未批准 mutation、跨 Workspace 访问和无效 Evidence 引用均为 0。

这些是单实例 release gate，不是公网服务 SLA。

## 安全基线

- 无认证/TLS 时只能绑定 loopback；配置非 loopback 必须 fail closed。
- 所有 credentials 使用 Secret reference，进程日志、Event、Artifact metadata 和 CI 产物无明文。
- 网络 connector 防重定向、DNS rebinding、localhost/private-range escape 和 credential-in-URL。
- 生产安全 profile 禁用 `exec` 和未隔离 Custom Tool。
- Extension、Runbook、Alert、Logs 和 Trace 都按不可信内容处理。
- Remediation 使用最小权限凭据、精确批准、kill switch、audit 和 reconciliation。
- 依赖、SBOM、许可证和供应链检查进入受保护 release environment。

## 可运维性

CLI 增加只读诊断命令：

```text
opscodex doctor
opscodex config validate
opscodex storage verify
opscodex storage backup
opscodex storage export --thread <id>
opscodex audit verify
```

`/healthz` 仅表示进程存活，`/readyz` 校验 store、schema 和必需 Workspace 配置；可选 Connector
故障显示 degraded，不应使所有 Workspace 不可用。

运维文档必须覆盖安装、配置、最小权限、容量、retention、备份、恢复、升级、回滚、Provider
故障、Connector 故障、SQLite corruption、NeedsReconciliation 和 Secret 泄露响应。

## 实施任务

### Task 1：冻结 v1 contracts

- Acceptance：API/Event/config/store/extension schema 有版本、兼容政策和 machine-readable fixtures。
- Verify：old-client/new-server、new-client/old-minor-server、unknown field/event、migration tests。
- Files：protocol/schema generation、fixtures、Web client、docs、CI drift check。

### Task 2：安全与隐私 hardening

- Acceptance：威胁模型中的每条边界有控制和测试；production-safe profile fail closed。
- Verify：SSRF/DNS、secret scan、path/symlink、extension injection、approval attack suite。
- Files：security modules/config、tests、workflow、threat model/docs。

### Task 3：性能、容量与长稳

- Acceptance：满足本阶段 SLO；资源达到 quota 时有界失败；无已知长期泄漏。
- Verify：benchmarks、24h soak、large Thread/artifact、4-turn load、disk-full tests。
- Files：bench/load harness、metrics、resource cleanup、CI/release scripts、docs。

### Task 4：运维与数据生命周期

- Acceptance：doctor/verify/backup/export/audit 可用；migration/rollback 演练有证据。
- Verify：fresh install、upgrade from every supported version、backup restore、corruption drill。
- Files：CLI commands、storage maintenance、release fixtures、docs、tests。

### Task 5：最终场景评测

- Acceptance：八类场景满足诊断、Evidence、安全和恢复标准；模型变化可比较基线。
- Verify：deterministic suite、provider contract matrix、受保护 real-provider gates。
- Files：scenario harness/fixtures/scorers、workflows、reports、docs。

### Task 6：发布与回滚

- Acceptance：签名或校验和、SBOM、release notes、artifact、升级/回滚说明完整；候选版演练通过。
- Verify：clean-machine install、artifact verification、release dry run、rollback rehearsal。
- Files：release workflow/scripts、packaging metadata、CHANGELOG、RELEASING、docs。

## 阶段门禁

- [最终产品目标](../PRODUCT_GOAL.md) 的全部完成标准有对应测试或审计证据。
- `v0.1-v0.6` 所有阶段门禁仍然通过，没有被后续版本弱化。
- 所有 Accepted ADR 与代码、配置、API 和文档一致。
- 八类 deterministic scenarios 全通过，关键 Claim 引用有效率 100%，无来源 Claim 为 0。
- 安全 suite 中未批准 mutation、跨 Workspace 访问、Secret 泄露均为 0。
- Crash/recovery matrix 中没有双重写操作；所有不确定状态进入 NeedsReconciliation。
- SLO、24h soak、容量和磁盘故障测试通过。
- 从每个受支持版本升级并恢复备份成功，回滚演练完成。
- Release artifact、SBOM、依赖审计、真实 Provider gate 和人工发布审查通过。
- 创建 annotated `v1.0.0` tag 和正式 GitHub Release 后，最终目标才标记完成。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 最后阶段继续加功能 | 高 | feature freeze；新增能力移到 v1.x/v2 目标 |
| “生产就绪”被理解为多租户 HA | 高 | 明确单实例边界和非目标 |
| Provider 波动导致 gate 不稳定 | 中 | deterministic suite 为主，真实 gate 少量且可重试有界 |
| 兼容承诺阻止修复错误设计 | 中 | v1 前集中修正，v1 后 additive + major policy |
| 长稳和迁移问题发现过晚 | 高 | 从 v0.5 起持续运行 crash/soak/migration suite |
